# Кодовый замок

## 1. Задание

В новой партии замков слово «Opened» появляется даже тогда, когда механизм не выдаёт квитанцию. Внутри — поле из 55 рядов по 55 узлов. Контроллер запоминает результаты прохода и сверяет их после последнего ряда.
Восстановите маршрут, после которого замок выдаёт настоящую квитанцию. Приложение предназначено для Windows x64. Символы маршрута различают регистр. -->

## 2. Анализ

Текст прочитан непосредственно с изображения размером 446×561. Второй файл, `locker.exe`, — консольный PE32+ для x86-64, SHA-256 `c4fff88b2cdfd85ed5551cba12e04a8920ccbec2aafd2199e0036ef2ea4b1f80`. Для статического анализа использованы REA/Ghidra, GNU strings, objdump и xxd. Команды первичного осмотра:

```sh
file Task.png locker.exe
objdump -h locker.exe
objdump -p locker.exe
strings -tx locker.exe | rg 'L55VM3|0123456789ABC|Route \(|Opened\.'
```

В файле шесть секций: `.text`, `.rdata`, `.data`, `.pdata`, `.tls`, `.reloc`. Среди импортов есть `fgets`, `puts` и `putchar`. В `.rdata` найдены следующие строки (слева — смещение от начала файла):

```text
  7c40 L55VM3
  7c70 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrs
 4f374 Route (55 symbols):
 4f389 Opened.
```

Ghidra показала, что в функции `FUN_00402e80` вызов печати `Opened.` по адресу `0x4038f8` предшествует решающему переходу `jne 0x403c6b` по адресу `0x40390a`. Этот переход пропускает печать квитанции, если проверка маршрута выявила несовпадение или сработала проверка отладчика.

## 3. Решение

1. **Декодировать поле.** С файлового смещения `0x8514` (виртуальный адрес `0x409f14`) прочитать `0x46e60` байт. Начальное значение генератора — `0x7335356c`. Перед каждым байтом выполнить `s = (1664525*s + 1013904223) mod 2^32` и применить XOR со старшим байтом `s`. Результат разбивается на 55×55 программ по 96 байт, каждая содержит 12 инструкций.
2. **Отобрать узлы по CRC.** Вызов `FUN_00403d00` по адресу `0x403140` исполняет программу выбранного узла. Все узлы одного ряда стартуют с одинаковыми пятью 32-битными регистрами из таблицы по адресу `0x4096c0`. После исполнения пятый регистр должен равняться CRC32 первых четырёх, записанных в little-endian. Проверка всех 3025 узлов оставляет ровно два кандидата в каждом ряду.
3. **Связать пары рядов.** Таблица с файлового смещения `0x847c` содержит 19 записей вида `<BB2xI`: два номера ряда и ожидаемый XOR их первых регистров. Например, `r0[0] ^ r0[50] == 0xd54fac40`, где `r0[i]` — первый регистр выбранного узла ряда `i`. Для каждой пары подходят две комбинации. Вместе с 17 непарными рядами получается 36 двоичных выборов.
4. **Восстановить маршрут по двум суммам.** Для каждого ряда программа берёт два 64-битных коэффициента `a, b` из таблицы по адресу `0x409b0c`. Вклад в первую сумму равен `ROL64((r1 << 32) | r2, r3 & 63) ^ a`, во вторую — `((r3 << 32) | r0) * b`. Цели по модулю 2⁶⁴ равны `0x9ffaf4686bbcc642` и `0xdb1ef47d9df86648`. Поиск встречей посередине перебирает по 2¹⁸ вариантов на половину. Для каждого варианта второй половины решатель ищет в первой дополнение сразу до обеих целей. Индексы выбранных столбцов переводятся в символы алфавита.
5. **Получить квитанцию.** Вход SHA-256 состоит из 12 байт `L55/route/3\0` с завершающим нулём, 55 числовых индексов столбцов и 1100 байт конечных состояний в порядке рядов. Первые 25 байт хеша складываются по XOR с 25 байтами из файла по смещению `0x7ca7`. Это воспроизводит значения, передаваемые в `putchar` начиная с `0x403ae4`.

Воспроизведение при помощи Python 3, без запуска EXE:

```text
$ python3 solve.py
…
Route: RQaC8hcgWjICQdqUGb2aV6c2Tr68AcUkdBqbdbgos8UkIS2FXhDQZLH
SHA-256: 855adcfe2f9aadfde6c94e5fcde869d7854552cc6cf46e8bdfd25c1f8dfbefd7
Receipt: b'flag{vm55_delayed_3ac971}'
```

## 4. Флаг

`flag{vm55_delayed_3ac971}`

## 5. Выводы

CRC каждого ряда оставляет два варианта. Маршрут определяют связи между рядами и две общие суммы. Подтверждением служит квитанция, восстановленная из хеша индексов и состояний всех 55 узлов.
