# Сработка

## Условие

По `traffic.pcap` и разметке из `note.txt` нужно найти 16-байтовую сигнатуру. Событие задаётся парой из клиентского порта и `X-Request-ID`. В записке отмечены шесть сработок и 30 пропусков.

## Summary

В дампе есть JavaScript клиента, который упаковывает записи в зависимости от состояния соединения. Восстанавливаем исходные блоки и находим сигнатуру как XOR второго и третьего блоков.

## Solution

### Восстановить записи клиента

В первом TCP-потоке лежит JavaScript в HTTP-ответе с `Transfer-Encoding: chunked` и `Content-Encoding: gzip`. Оттуда берём перестановки, сдвиги и формулу маски для трёх режимов. Для размеченных портов собираем TCP по sequence number и сопоставляем запросы с ответами.

`/open` и `/reset` задают режим, seed и нулевой счётчик. Смена режима применяется при `X-Commit`. Подтверждённое событие обновляет seed и счётчик один раз. Поэтому сначала обращаем маску, сдвиги и перестановку запроса по состоянию на момент отправки, затем учитываем ответ. Для повторного `X-Request-ID` берём уже восстановленную запись.

### Сверить сигнатуру

Запись состоит из трёх блоков по 16 байт. Перебираем три пары блоков и проверяем их XOR по разметке. Только XOR второго и третьего блоков даёт одно значение на всех шести сработках, ни разу не встречающееся у 30 пропусков.

Из каталога `liga-ctf` запускаем [скрипт](solvers/state-tcp.py) на исходных вложениях. Нужны Python 3.10+ и `tshark`.

```bash
python3 solvers/state-tcp.py traffic.pcap note.txt
```

Сигнатура `24602d333832372e27273121310c2436` после XOR с повторённым ключом `TSPU` даёт `p3}flag{state_tc`. Переносим первые три байта в конец по инструкции из записки.
