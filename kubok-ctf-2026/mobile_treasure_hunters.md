# Mobile Treasure Hunters — восстановление удалённой переписки

**Результат:** восстановлены 12 сообщений; подлинность каждого проверена при расшифровании AES-GCM. Флаг на платформу не отправлялся.

## Summary

На изъятом телефоне сообщения мессенджера Burnt Note самоуничтожались, а после полной очистки таблица переписки пуста. Нужно восстановить последнее сообщение. Даны APK приложения и архив с файлами телефона.

**APK** — пакет Android-приложения. Его код помогает понять формат данных и алгоритм шифрования. **SQLite** — встроенная файловая система управления базами данных; файлы базы и её журнал изменений могут содержать данные, которые больше не видны обычным SQL-запросом.

Гипотеза: очистка удалила ссылки на записи, но предыдущие версии страниц SQLite сохранились в журнале или не были физически затёрты. Вторая задача — восстановить ключи: сами сообщения зашифрованы, поэтому одной корректной базы недостаточно. Ниже обе части проверяются независимо.

## Solution

### Что понадобится

Python 3, модуль `cryptography`, SQLite CLI, `tar`, `exiftool`. Для изучения APK также пригодится `jadx`. Проверено с `cryptography 50.0.2` и SQLite `3.54.0`. Все команды ниже выполняются из каталога `mobile-forensics/work` внутри набора задачи. Файл `solve.py` находится рядом с этим райтапом в каталоге `work`; он использует именно относительные пути из этой рабочей директории.

Рабочая копия исходных файлов уже подготовлена. Для повторного распаковывания архива в отдельной чистой копии можно выполнить:

```bash
mkdir -p data-copy
 tar -xzf attachments/evidence.tar.gz -C data-copy
```

Для запуска приложенного скрипта нужны исходно распакованные каталоги `data/` и `sdcard/` непосредственно в `work/`; если их ещё нет, из `work/` выполните `tar -xzf attachments/evidence.tar.gz`. Не запускайте APK: для решения достаточно статического анализа, то есть изучения кода без его исполнения.

## 1. Найти следы переписки и ключевого материала

В `data/data/com.ctf.burntnote/databases/` находятся `messages.db` и `messages.db-wal`. Суффикс `-wal` обозначает **write-ahead log**, журнал SQLite, куда записываются новые версии страниц базы. Даже когда финальная версия таблицы пуста, в WAL может сохраняться более ранняя версия.

Осмотрите диагностический журнал:

```bash
cat data/data/com.ctf.burntnote/files/diagnostics.log
```

Значимые строки реального вывода:

```text
storage: local db v3 opened (wal)
im-backup parsed: com.whatsapp/databases/msgstore.db (legacy plaintext)
chrome profile scanned: app_chrome/Default/History
camera roll scanned: 1 candidate(s)
seed fragment captured (device entropy): 3d91968bd7ed
seed material sealed: 4/4
master key derived: ok (pbkdf2 100000)
total wipe executed: messages=12
```

Здесь `seed` — исходный материал, из которого приложение выводит ключ. Журнал указывает четыре фрагмента и источники части из них; это подсказка для анализа, а не самостоятельное доказательство правильного ключа.

## 2. Собрать четыре фрагмента

**WhatsApp.** Запросите сообщения из резервной базы:

```bash
sqlite3 data/data/com.whatsapp/databases/msgstore.db \
  "select timestamp, text_data from messages where remote_resource like '%burntnote%';"
```

Найдено сообщение с фрагментом `5a1b2ef44061` и временем Unix `1768320131`. **Unix-время** — число секунд после 1 января 1970 года UTC.

**Фотография.** EXIF — служебные метаданные изображения; в них могут находиться дата съёмки и пользовательский комментарий:

```bash
exiftool sdcard/DCIM/Camera/IMG_20260113_192401.jpg | \
  rg 'Date/Time Original|Offset Time Original|User Comment'
```

Вывод содержит дату `2026:01:13 19:24:01`, пояс `+03:00` и `User Comment: 64574c90358d`.

**Диагностика.** В приведённой выше строке `seed fragment captured` находится `3d91968bd7ed`. Число в квадратных скобках — время в миллисекундах Unix: `1768321862011`.

**История Chrome.** Исследуется файл из предоставленного образа телефона, не профиль браузера рабочего компьютера:

```bash
sqlite3 'file:data/data/com.android.chrome/app_chrome/Default/History?immutable=1' \
  "select url,last_visit_time from urls where url like '%burntnote%';"
```

Вывод:

```text
https://paste.burntnote.onion/k/ae4fa6e83015|13412796333000000
```

Последний компонент URL — `ae4fa6e83015`. Chrome хранит это время в микросекундах с 1601 года UTC. В URL переходить не требуется: значение уже находится в локальном артефакте.

Четыре значения в порядке времени объединяются через дефис:

```text
5a1b2ef44061-64574c90358d-3d91968bd7ed-ae4fa6e83015
```

Единообразно сравнить времена можно так:

```bash
python3 - <<'PY'
from datetime import datetime, timezone
items = [
    ('WhatsApp', 1768320131),
    ('EXIF', datetime.fromisoformat('2026-01-13T19:24:01+03:00').timestamp()),
    ('diagnostics', 1768321862011 / 1000),
    ('Chrome', 13412796333000000 / 1000000 - 11644473600),
]
for name, timestamp in items:
    print(name, datetime.fromtimestamp(timestamp, timezone.utc).isoformat())
PY
```

Соль берётся из Android ID — идентификатора устройства в образе:

```bash
rg 'android_id' data/secure/0/settings_secure.xml
```

Получено `426079c78484367a`. **Соль** — дополнительное значение для функции получения ключа; здесь используются ASCII-байты строки, а не байты, полученные декодированием шестнадцатеричной записи.

## 3. Понять схему шифрования приложения

Декомпилировать APK можно командой из `work/`:

```bash
jadx -d jadx attachments/burntnote.apk
```

**Декомпиляция** превращает машинно-ориентированный код приложения в приближённый к исходному Java-код. Названия в нём обфусцированы — намеренно заменены нечитаемыми именами. Строки тоже защищены; алгоритм их преобразования находится в `jadx/sources/com/decryptstringmanager/DecryptString.java`. В подготовленной рабочей папке результаты раскрытия строк уже сохранены в `decoded/`.

Начать изучение можно с поиска параметров и операций:

```bash
rg -n 'PBKDF2|100000|1400|GCM|Hmac|SHA256' decoded/
```

Из исследованного кода и проверенного восстановителем алгоритма следует:

1. `PBKDF2-HMAC-SHA256` получает из объединённых фрагментов и ASCII Android ID 32 байта за 100000 итераций. PBKDF2 — функция выведения ключа из пароля, намеренно повторяющая вычисления много раз.
2. Начальный ключ получается как `HMAC-SHA256(master, b'burnt-note/root')`. HMAC — функция аутентификации с секретным ключом; здесь её используют для получения нового ключа.
3. Для каждого сообщения применяется AES-GCM с отдельным `nonce` из таблицы и дополнительными данными `burnt-note/msg/<id>`. **Nonce** — значение, используемое при шифровании конкретной записи. **AAD** — данные, которые проверяются на целостность вместе с сообщением, хотя не входят в зашифрованный текст.
4. Открытый текст имеет фиксированный размер 1400 байт и дополнен нулями. Для отображения нули можно убрать, но для следующего ключа нужны все 1400 байт.
5. Следующий ключ: `HMAC-SHA256(current_key, plaintext_padded + b'|burnt-note/step|<next_id>')`.

Последняя зависимость образует цепочку: без корректного сообщения № 2 нельзя получить ключ для № 3, и аналогично для остальных. Поэтому важно восстановить даже записи, удалённые до полной очистки.

## 4. Восстановить состояние до полной очистки

Страница SQLite — блок фиксированного размера. WAL состоит из заголовка и кадров: каждый кадр содержит номер изменённой страницы и её новую версию. Ненулевой размер базы в заголовке кадра отмечает конец зафиксированной транзакции. Просмотреть номера кадров можно без внешних библиотек:

```bash
python3 - <<'PY'
import struct
from pathlib import Path
w = Path('data/data/com.ctf.burntnote/databases/messages.db-wal').read_bytes()
s = struct.unpack_from('>I', w, 8)[0]
print('WAL page size:', s)
for i in range((len(w) - 32) // (24 + s)):
    page, commit = struct.unpack_from('>II', w, 32 + i * (24 + s))
    print(i + 1, page, commit)
PY
```

Проверенный вывод: размер страницы `4096`, затем пары `кадр номер_страницы размер_после_фиксации`:

```text
1 1 0
2 2 0
3 3 0
4 7 0
5 8 8
6 1 0
7 3 0
8 4 8
```

После кадра 5 первая транзакция зафиксирована, после кадра 8 — следующая. Скрипт `solve.py` берёт копию основной базы, последовательно накладывает первые пять кадров и обрезает результат до восьми страниц. Так получается согласованное состояние до последней очистки. В ранее созданной диагностической копии это видно так:

```bash
sqlite3 'file:snapshot5.db?immutable=1' 'select group_concat(id) from messages;'
sqlite3 'file:snapshot8.db?immutable=1' 'select count(*) from messages;'
```

Фактический результат: в первой копии `1,3,5,6,7,8,9,10,11,12`; во второй — `0`. Файлы `snapshot5.db` и `snapshot8.db` являются промежуточными результатами исследования и для запуска финального восстановителя не требуются.

### Вернуть записи 2 и 4

В снимке после пятого кадра отсутствуют ID 2 и 4. SQLite хранит строки таблицы в **ячейках** страниц B-дерева, а в начале страницы — массив указателей на актуальные ячейки. При удалении ссылки могут исчезнуть раньше, чем перезапишутся сами байты.

На страницах 4 и 5 по смещению `1206` от начала каждой страницы сохранились ячейки. Проверяем сигнатуру непосредственно в снимке:

```bash
python3 - <<'PY'
from pathlib import Path
b = Path('snapshot5.db').read_bytes()
for page in (4, 5):
    pos = (page - 1) * 4096 + 1206
    print('page', page, 'offset 1206:', b[pos:pos+4].hex(' '))
PY
```

Ожидаемые по проверкам восстановителя байты: `8b 22 02 07` и `8b 22 04 07`. Первые два байта кодируют размер полезной нагрузки SQLite в формате varint; следующий байт — ID строки, последний относится к заголовку записи. Байты совпадают с ID искомых записей. Смещение `1206` — результат анализа именно этого образа, а не универсальная константа SQLite.

В `solve.py` для этих страниц проверяются тип страницы `0x0d` (листовая страница таблицы) и указанные байты. Затем устанавливаются количество ячеек `2`, начало области содержимого `1206` и второй указатель на `1206`. Первый указатель существующей записи сохраняется. Результат записывается в отдельный `recovered.db`: исходные `messages.db` и WAL не изменяются.

Ограничение: эти точные исправления и число кадров рассчитаны на предоставленный образ. На другой базе смещения и структура будут другими; перед редактированием нужны отдельный анализ страниц и сохранение копии.

## 5. Расшифровать цепочку

Из каталога `work/` запустите:

```bash
python3 solve.py
```

Скрипт проверяет целостность SQLite, наличие всех ID от 1 до 12 и вызывает AES-GCM для каждой строки. AES-GCM проверяет тег подлинности: если ключ, зашифрованные данные или AAD неверны, библиотека выдаёт ошибку вместо подтверждённого текста. После каждого успешного расшифрования вычисляется следующий ключ из **полного дополненного** текста.

Фрагмент реально полученного вывода:

```text
8: Вторая — двор за школой, у синих гаражей.
10: Последняя самая важная. Сделаешь — сожги все переписки.
11: Готово. Три из трех. Сейчас все сожгу.
12: Подтверждаю приём. Контрольная фраза: ctfcup{ch41n_0f_4sh3s}. Сожги и это.
```

Проверка сформированной базы:

```bash
sqlite3 'file:recovered.db?immutable=1' \
  'pragma integrity_check; select count(*) from messages;'
```

Реальный вывод:

```text
ok
12
```

`integrity_check` подтверждает внутреннюю согласованность структуры SQLite, но само по себе не доказывает правильность открытого текста. Для этого существенно, что все 12 тегов AES-GCM проверились и сообщения декодировались в осмысленный текст.

## 6. Проверка важности ключа и AAD

Сравним правильное расшифрование первого сообщения с двумя намеренно неправильными вариантами. Запустить после `solve.py`:

```bash
python3 - <<'PY'
import hashlib, hmac, sqlite3
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag
c = sqlite3.connect('file:recovered.db?immutable=1', uri=True)
nonce, frame = c.execute('select nonce, frame from messages where id=1').fetchone()
p = b'5a1b2ef44061-64574c90358d-3d91968bd7ed-ae4fa6e83015'
m = hashlib.pbkdf2_hmac('sha256', p, b'426079c78484367a', 100000, 32)
k = hmac.digest(m, b'burnt-note/root', 'sha256')
for name, key, aad in [
    ('correct', k, b'burnt-note/msg/1'),
    ('wrong AAD', k, b'burnt-note/msg/2'),
    ('wrong key', bytes([k[0] ^ 1]) + k[1:], b'burnt-note/msg/1'),
]:
    try:
        AESGCM(key).decrypt(nonce, frame, aad)
        print(name, 'OK')
    except InvalidTag:
        print(name, 'InvalidTag')
PY
```

Реальный вывод:

```text
correct OK
wrong AAD InvalidTag
wrong key InvalidTag
```

Эта проверка показывает, что успешный результат зависит и от ключа, и от идентификатора в AAD. Она не является отдельным доказательством каждого промежуточного шага сбора фрагментов, но подтверждает согласованность полученного ключа с первой записью.

## Как узнать подобную задачу в будущем

Признаки: пустая таблица рядом с непустым `-wal`, упоминания самоудаления, несоответствие количества строк и следов в логах, а также APK рядом с файловым образом. Сначала сохраняйте оригиналы, исследуйте зафиксированные состояния журнала и следы удалённых ячеек; затем изучайте, как приложение получает ключи и связывает сообщения. Сверяйте гипотезы проверками целостности базы и криптографических тегов.

## Что осталось непроверенным

Условие обещает контрольную фразу с адресом финальной точки, однако в самом последнем расшифрованном сообщении адреса нет. Сообщение № 8 упоминает двор за школой у синих гаражей как вторую точку, а не как подтверждённую финальную. Более точный адрес по восстановленному тексту устанавливать нельзя. Отправка флага и проверка платформой не выполнялись.
