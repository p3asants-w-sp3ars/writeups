# Noise in space

## Summary

Нам дали запись радиосигнала, программу её обработки и файл с инструкциями для этой программы. В инструкциях два подозрительных нуля: первый мешает настроиться на частоту сигнала, второй стирает вычисленный параметр преобразования речи. После исправления обоих значений получается разборчивая запись с фразой **Tune the noise**.

**Результат:** флаг `ctfcup{tune_the_noise}` сдан и верифицирован на платформе; фраза также подтверждена локальным распознаванием речи.

Для повторения нужны Linux x86-64, Python 3 с NumPy и SciPy, `unzip`, `file`, `xxd`, `sha256sum`, `bwrap` и аудиоплеер. Для автоматической расшифровки дополнительно нужны `faster-whisper` и локальная модель. В этом окружении использовались NumPy 2.5.4, SciPy 1.18.1 и faster-whisper 1.2.1. Проверка Python-зависимостей:

```bash
python3 -c 'import numpy, scipy; print(numpy.__version__, scipy.__version__)'
```

Вывод [запущено при подготовке райтапа]:

```text
2.5.4 1.18.1
```

Установку недостающих Python-пакетов можно выполнить в виртуальном окружении внутри рабочей папки: `python3 -m venv .venv`, затем `.venv/bin/pip install numpy scipy faster-whisper`. Проверить внешние инструменты можно командой `command -v unzip file xxd sha256sum bwrap`. Модель распознавания при этом отдельно должна быть доступна локально.

## Solution

### 1. Что дано и на что намекает условие

Начинаем в папке задачи; команды ниже предполагают, что распакованные файлы находятся в `work/`. Посмотрим содержимое архива:

```bash
unzip -l work/attachments/task.zip
```

Вывод [запущено при подготовке райтапа]:

```text
   Length      Date    Time    Name
---------  ---------- -----   ----
 24463040  2026-10-28 21:35   capture.iq
    58992  2026-10-28 21:35   dsp_vm
      156  2026-10-28 21:35   kernel.kdsp
```

`unzip -l` перечисляет файлы архива без распаковки. Здесь `capture.iq` содержит отсчёты сигнала, `dsp_vm` обрабатывает их, а `kernel.kdsp` задаёт последовательность операций. В условии сказано: «НЕ ДОВЕРЯЙ НУЛЮ. ОН СЛИШКОМ УДОБНЫЙ». Это не доказывает, какие нули нужно менять, но даёт направление для поиска после изучения обработки.

```bash
file work/dsp_vm work/kernel.kdsp work/solved.wav
```

Вывод [запущено при подготовке райтапа]:

```text
work/dsp_vm:     ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped
work/kernel.kdsp: data
work/solved.wav: RIFF (little-endian) data, WAVE audio, Microsoft PCM, 16 bit, mono 48000 Hz
```

`file` определяет возможный тип по содержимому. ELF — формат исполняемых файлов Linux; `x86-64` означает архитектуру обычных 64-битных ПК. `statically linked` означает, что основные зависимости включены в программу; `stripped` — что обычные имена функций удалены, что усложняет анализ. WAV — контейнер звука; здесь в нём один канал с частотой 48 000 отсчётов в секунду. Результат `file` для `capture.iq` оказался ошибочным определением по совпадению байтов, поэтому расширение или такой вывод сами по себе не доказывают формат данных.

## 2. Что делают `dsp_vm` и ядро

**DSP** — цифровая обработка сигналов: вычисления над последовательностью чисел, представляющих сигнал. `dsp_vm` — программа-виртуальная машина: она читает не машинный код процессора из `kernel.kdsp`, а собственные короткие инструкции и выполняет соответствующие им операции. Здесь слово «ядро» обозначает этот файл инструкций обработки, а не ядро Linux.

Внутри виртуальной машины есть регистры `R2`, `R3` и другие. В этом контексте регистр — именованная ячейка для промежуточного значения. Инструкция может, например, записать число в регистр или запустить обработку, взяв из разных регистров вход и настройки.

При предыдущем анализе `dsp_vm` с помощью `r2` (radare2, инструмент для изучения исполняемых файлов) были установлены смысл значимых инструкций и формат ядра. Сохранённый дизассемблированный машинный код доступен в `work/vm_disasm.txt`, `work/dsp_disasm.txt` и `work/demod_disasm.txt`. Дизассемблирование — представление машинных байтов как команд процессора; интерпретация инструкций KDSP ниже получена из анализа программы, а не из имён в файле.

Посмотрим байты ядра:

```bash
xxd -g 1 -s 0x60 -l 48 work/kernel.kdsp
```

`xxd` печатает байты в шестнадцатеричной системе: в ней один байт записывается двумя символами от `0` до `f`. `-g 1` показывает байты по одному, `-s 0x60` начинает с позиции 0x60, а `-l 48` ограничивает вывод 48 байтами. Позиция, или смещение, отсчитывается от начала файла с нуля; `0x` обозначает шестнадцатеричное число.

Вывод [запущено при подготовке райтапа]:

```text
00000060: 00 00 30 01 00 30 42 21 57 13 50 01 68 24 60 01
00000070: 00 60 55 07 09 00 60 01 04 00 66 08 00 60 55 06
00000080: df 39 70 01 00 50 87 07 00 00 80 01 00 80 94 22
```

Каждая инструкция занимает четыре байта. Существенные инструкции после анализа VM:

| Смещение | Байты | Смысл |
| --- | --- | --- |
| `0x60` | `00 00 30 01` | Записать `0` в `R3`. |
| `0x64` | `00 30 42 21` | Обработать I/Q из `R2`, взяв частотный параметр из `R3`; сохранить результат в `R4`. |
| `0x88` | `00 00 80 01` | Записать `0` в `R8`. |
| `0x8c` | `00 80 94 22` | Преобразовать аудио из `R4`, используя параметр из `R8`; сохранить результат в `R9`. |

Значение «0 Гц передаётся ядром» означает конкретно: инструкция по адресу `0x60` кладёт число 0 в `R3`, и следующая инструкция использует этот регистр как частотный параметр. Это не означает, что входной сигнал состоит из нулевых частот.

## 3. Первая настройка: где находится сигнал

`capture.iq` содержит чередующиеся 32-битные числа с плавающей точкой: `I0, Q0, I1, Q1, ...`. Пара I и Q описывает один комплексный отсчёт `I + jQ`: это удобный способ хранить не только величину, но и фазу колебания, то есть положение в его цикле. Частота дискретизации записи — 240 000 таких пар в секунду; она установлена при изучении программы.

Чтобы найти заметный сигнал, оценим спектр — распределение мощности по частотам. Метод Уэлча разбивает запись на участки и усредняет их спектры, чтобы уменьшить влияние случайного шума.

```bash
python3 -c 'import numpy as np; from scipy.signal import welch; x=np.fromfile("work/capture.iq",dtype="<f4"); f,p=welch(x[::2]+1j*x[1::2],fs=240000,nperseg=16384,return_onesided=False); print("float32 values:",len(x)); print("complex samples:",len(x)//2); print("peak:",f[np.argmax(p)],"Hz"); print("resolution:",f[1]-f[0],"Hz")'
```

Здесь `<f4` означает четырёхбайтовые числа с плавающей точкой с младшим байтом первым; `x[::2]` берёт I, `x[1::2]` — Q. `fs` — частота отсчётов, `nperseg` — размер участка, `argmax` находит самый высокий пик.

Вывод [запущено при подготовке райтапа]:

```text
float32 values: 6115760
complex samples: 3057880
peak: 25004.8828125 Hz
resolution: 14.6484375 Hz
```

Самый сильный пик попал в ячейку около 25 005 Гц. Разрешение сетки около 14,65 Гц, поэтому разумная проверяемая настройка — **25 000 Гц**; один пик сам по себе не доказывает, что это нужное сообщение. Подтверждение здесь практическое: после обоих исправлений появляется разборчивая речь.

### Что означает «перенос по частоте»

Перенос — математическое преобразование всех частот сигнала на одинаковую величину. В данном случае настройка на 25 000 Гц перемещает область около этой частоты к нулю, то есть к центральной частоте представления:

```text
до преобразования:    24 800 Гц   25 000 Гц   25 200 Гц
после сдвига:           -200 Гц        0 Гц      200 Гц
```

Например, колебание на 25 200 Гц после сдвига вниз на 25 000 Гц оказывается на +200 Гц относительно нового центра. Отрицательная частота здесь не означает «звук ниже нуля»: в комплексном I/Q-представлении знак различает направления изменения фазы. После переноса дальнейшие операции могут выделить полезное содержимое вокруг нового центра.

При исходном `R3 = 0` никакой такой настройки на 25 кГц не происходит. Меняем значение, загружаемое в `R3`, на 25 000.

## 4. Вторая настройка: значение, которое затирают

Перед инструкцией `R8 = 0` ядро вычисляет число из нескольких констант. `^` — побитовый XOR: для каждой двоичной позиции результат равен 1, когда соответствующие биты отличаются. `<< 4` сдвигает биты влево на четыре позиции; для положительного целого это умножение на 16.

```bash
python3 -c 'a=0x1357 ^ 0x2468; b=9<<4; print(hex(a),b,hex(a+b),hex((a+b)^0x39df),(a+b)^0x39df)'
```

Вывод [запущено при подготовке райтапа]:

```text
0x373f 144 0x37cf 0xe10 3600
```

То есть `0x1357 XOR 0x2468 = 0x373f`; прибавляем 144 и получаем `0x37cf`; XOR с `0x39df` даёт `0xe10`, то есть 3600 в обычной десятичной записи. Результат попадает в `R8`, но следующая инструкция по смещению `0x88` сразу заменяет его нулём. Следующая DSP-операция поэтому получает ноль вместо 3600.

Это второй конкретный след подсказки. По анализу обработки и результату прослушивания параметр относится к частотному преобразованию аудио, исправляющему инверсию спектра речи. Инверсия спектра означает перестановку частот относительно опорной частоты: участки спектра, оказавшиеся «перевёрнутыми», возвращаются в порядок. Формулы и точный диапазон входов этой операции здесь дополнительно не доказываются; значение 3600 и его затирание проверяются по инструкциям, а полезность — по выходной записи.

Одна только замена первого нуля дала WAV, но речь оставалась неразборчивой. Это показывает, почему наличие звукового файла и правильной длины ещё не подтверждает правильную обработку.

## 5. Исправление и воспроизведение

В папке `work/solve.py` находится проверенный скрипт. Он проверяет исходные байты, заменяет ноль на 25 000 и заменяет инструкцию обнуления на сложение `R8` с нулём, сохраняющее 3600:

```python
from pathlib import Path

kernel = bytearray(Path("kernel.kdsp").read_bytes())
assert kernel[0x60:0x64] == bytes.fromhex("00 00 30 01")
assert kernel[0x88:0x8c] == bytes.fromhex("00 00 80 01")
frequency = ((0x1357 ^ 0x2468) + (9 << 4)) ^ 0x39df
assert frequency == 3600
kernel[0x60:0x62] = (25000).to_bytes(2, "little")
kernel[0x88:0x8c] = bytes.fromhex("00 00 88 03")
Path("kernel_solved.kdsp").write_bytes(kernel)
print(f"IQ frequency: 25000 Hz; audio inversion frequency: {frequency} Hz")
print("Wrote kernel_solved.kdsp")
```

`assert` останавливает программу, если байты исходного файла не совпали с ожидаемыми. `bytearray` позволяет менять отдельные байты. `to_bytes(2, "little")` представляет число двумя байтами, начиная с младшего: 25 000 = `0x61a8`, поэтому в файле будет `a8 61`.

Далее все команды выполняются из `work/`:

```bash
cd work
python3 solve.py
```

Вывод [получен при предыдущем решении]:

```text
IQ frequency: 25000 Hz; audio inversion frequency: 3600 Hz
Wrote kernel_solved.kdsp
```

Запускаем предоставленный исполняемый файл в изолированном окружении. Чужие бинарные файлы не следует запускать непосредственно в основной системе. `bwrap` создаёт изолированное пространство; `--unshare-all` отключает разделение в том числе сетевого пространства с основной системой, `--bind` даёт доступ к текущей папке, а `/tmp`, `/proc` и `/dev` подготавливают минимальное окружение:

```bash
bwrap --unshare-all --die-with-parent \
  --bind "$PWD" /data --tmpfs /tmp --proc /proc --dev /dev \
  --chdir /data \
  /data/dsp_vm /data/capture.iq /data/kernel_solved.kdsp /data/solved.wav
```

`$PWD` — путь текущей папки, `/data` — её имя внутри окружения. Три аргумента программы — запись, исправленное ядро и выходной WAV. Проверьте результат:

```bash
sha256sum solved.wav
```

Вывод [воспроизведён при подготовке райтапа на отдельном выходном файле]:

```text
69f0eb7fc6e7ef67f5c60fa18ce1093c158aa37a252815f086ef43132a86d08b  solved.wav
```

SHA-256 — контрольная сумма содержимого: совпадение здесь позволяет проверить, что получился тот же файл. Выше показано имя `solved.wav`; при проверке использовался отдельный файл `writeup_check.wav` с той же суммой.

### 6. Сообщение и флаг

Прослушайте `solved.wav` любым плеером. При предыдущем локальном запуске модели `faster-whisper-small` получилось:

```text
Receiver service message, the calibration phrase follows.
Tune the noise.
I repeat, tune the noise.
End of service message.
```

Платформа приняла флаг `ctfcup{tune_the_noise}`.

## Если результат отличается

- Если `assert` сработал, убедитесь, что используется исходный `kernel.kdsp` из архива и работа ведётся с файлами этой задачи.
- Если `bwrap` не запускается, проверьте доступность пользовательских пространств имён в системе. Без изоляции не запускайте незнакомый `dsp_vm` в основной системе.
- Если сумма WAV отличается, проверьте версию входного архива и то, что программа получила именно `kernel_solved.kdsp`. Различие суммы означает различие файлов, но само по себе не объясняет причину.
- Если речь неразборчива, убедитесь, что внесены оба исправления: сдвиг на 25 000 и сохранение вычисленного значения 3600.

## Самопроверка и словарь

1. Почему пик около 25 кГц позволяет предложить настройку 25 000 Гц, но не доказывает её правильность?
2. Какое значение окажется в `R8`, если оставить инструкцию по `0x88` без изменения?
3. Куда попадёт составляющая 25 300 Гц после сдвига вниз на 25 000 Гц?

**I/Q** — пара чисел для комплексного представления отсчёта; **частота дискретизации** — число отсчётов в секунду; **спектр** — распределение сигнала по частотам; **виртуальная машина** — программа, исполняющая свой набор инструкций; **регистр** — ячейка промежуточного значения; **XOR** — побитовая операция различия; **смещение** — позиция байта от начала файла.

Команды: `unzip -l` перечисляет архив; `file` определяет вероятный тип; `xxd` показывает байты; `python3 solve.py` создаёт исправленное ядро; `bwrap` запускает обработчик в изоляции; `sha256sum` проверяет выходной файл.
