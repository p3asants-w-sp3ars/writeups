# My Own FS

## Summary

В задании дана самодельная файловая система и образ диска. Восстанавливаем удалённый PNG напрямую из inode, хотя запись в таблице занятости уже помечена свободной: содержимое inode и ссылки на следующие блоки не очищены. Категория: forensics/filesystem; инструменты: Python 3 и просмотрщик PNG.

Флаг на восстановленной картинке: `ctfcup{dbf75e112fef01db44b2a0e68ab2065e}`. Я проверил его чтением пиксельного изображения; автоматический OCR не является источником этого значения. Проверка принятия флага платформой в локальных материалах не сохранена.

## Solution

### Что понадобится

- Python 3. Скрипт использует только стандартную библиотеку, сторонние пакеты устанавливать не нужно.
- Файловый образ `disk.img` из архива задачи.
- Любая программа для просмотра PNG, если нужно подтвердить строку флага глазами.

### Как устроен образ

Исходный код файловой системы в `my-own-fs/myfs/src/main.rs` документирует формат диска. Размер inode равен 1337 байтам; перед областью inode находится массив занятости размером `N` байт, где `N = размер_образа / 1338`. Один байт массива соответствует одному inode: `0` означает свободный, ненулевой — занятый.

Смещение inode `i` вычисляется так:

```text
N + i * 1337
```

Первые 4 байта inode — little-endian-номер следующего inode в цепочке, байт со смещением 4 задаёт тип. У первого inode файла заголовок занимает 51 байт; в нём восьмибайтовый размер файла хранится со смещения 15. У продолжений заголовок занимает 5 байт. Поэтому для восстановления недостаточно прочитать один inode: нужно пройти цепочку и склеить данные после соответствующих заголовков, остановившись на объявленном размере.

Обычный поиск по каталогу не находит удалённый файл: каталог содержит только живые записи, а inode файла отмечен свободным. Но освобождение inode изменило только байт занятости. Остальные байты, включая размер, тип, содержимое и ссылки цепочки, остались на месте.

### Воспроизведение

Сначала проверим входной образ:

```bash
file disk.img
```

Контрольный результат для образа:

```text
disk.img: data
```

Образ не обязан распознаваться как ext4 или другая распространённая файловая система: это собственный формат из задания. Восстановитель разбирает структуру напрямую.

Реализация по приведённому ниже алгоритму должна прочитать inode `2979` и записать результат в `recovered.png`. Контрольный вывод такого восстановления:

```text
image=my-own-fs/disk.img sha256=d06334f6525305d2168b9484cf0fb8cf2e763a2499d5ebf005eefd8f1edc251a
inode_count=3134 allocated=3
visible inode=0 path=/ type=2
recovered inode=2979 allocated=False size=214153 chain_length=161 output=recovered.png
chain_head=[2979, 1451, 1565, 2240, 497, 2872, 562, 672, 1778, 2931, 3058, 202] chain_tail=[142, 150, 1782, 3050, 127]
magic=b'\x89PNG\r\n\x1a\n' sha256=a1d3077fb6dcb12c8d84ca449552226756505414279f492449dae08929e4c90f
```

`allocated=False` подтверждает, что inode 2979 свободен согласно таблице занятости. При этом его заголовок всё ещё указывает размер 214153 байта и цепочку из 161 inode. `magic` — первые восемь байт восстановленного файла; последовательность `89 50 4e 47 0d 0a 1a 0a` является сигнатурой PNG.

Проверим тип и размер извлечённого файла:

```bash
file recovered.png
```

Ожидаемая контрольная точка:

```text
recovered.png: PNG image data, 900 x 160, 8-bit/color RGB, non-interlaced
```

Откройте `recovered.png` в просмотрщике изображений. На картинке читается:

```text
ctfcup{dbf75e112fef01db44b2a0e68ab2065e}
```

### Ключевой код восстановителя

`MyFs` читает образ как массив байтов. Число inode вычисляется делением размера образа на 1338 (`1337` байт inode плюс один байт записи занятости). Для inode `i` скрипт берёт его байты начиная с `N + i * 1337`.

Минимальный фрагмент, достаточный для восстановления файла:

```python
count = len(image) // 1338
offset = count + inode * 1337
next_inode = struct.unpack_from("<I", image[offset:], 0)[0]
size = struct.unpack_from("<Q", image[offset:], 15)[0]

for index, inode in enumerate(chain):
    block = image[count + inode * 1337:count + (inode + 1) * 1337]
    header = 51 if index == 0 else 5
    output.extend(block[header:])
result = bytes(output[:size])
```

Метод `chain()` последовательно читает первые четыре байта каждого inode как указатель на следующий inode. Ноль завершает цепочку. `read_file()` читает размер из заголовка первого inode, пропускает 51 байт в первом блоке и 5 байт в каждом продолжении, затем соединяет данные и обрезает результат ровно до объявленного размера. Метод намеренно не требует, чтобы inode был помечен занятым: это позволяет восстановить удалённую запись, пока её содержимое ещё не затёрто.

После извлечения скрипт также обходит каталоги от inode 0. Это объясняет, почему удалённый PNG не появляется среди видимых файлов: корневой каталог существует, но ссылка на удалённый inode в нём отсутствует.

### Почему восстановление возможно

Удаление в этой файловой системе не стирает данные inode. Оно меняет лишь соответствующий байт таблицы занятости на `0`, чтобы allocator мог повторно использовать слот. Пока новый файл не перезаписал этот inode или его блоки, старый размер и ссылки на продолжения остаются пригодны для чтения.

Это типичный принцип восстановления удалённых файлов: удаление часто убирает ссылки на данные, а не немедленно затирает сами данные. Здесь формат специально упрощён, поэтому можно обойти стандартный интерфейс файловой системы и прочитать сохранённые структуры напрямую.

### Проверки и границы

- Восстановление извлекло inode 2979 размером 214153 байта по цепочке из 161 inode.
- Полученный PNG распознан как изображение 900×160 RGB и визуально содержит флаг.
- Скрипт не проверяет флаг на сервере соревнования. Успешная отправка флага платформе здесь не подтверждается.
- Если inode или его продолжения были бы повторно использованы и перезаписаны, эта цепочка могла бы указывать на повреждённые или посторонние данные. В текущем образе сигнатура PNG и корректно распознанное изображение подтверждают успешное восстановление.
